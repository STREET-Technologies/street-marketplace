# Web social sign-in provider requirements

Verified against official provider documentation on 2026-10-31. This is a staging implementation prerequisite note, not evidence that STREET's provider consoles or deployed configuration are ready. No credentials, environment files, or provider consoles were inspected or changed.

## Google Identity Services

- Use a Google OAuth client of type **Web application**. Register the exact marketplace staging origin in Authorized JavaScript origins. Origins contain scheme and host (plus a non-default port), not a route. For this repository's local development, register both `http://localhost` and `http://localhost:4319`. Configure the application's branding, support contact and policy links. A JavaScript popup callback does not require registering a redirect endpoint; redirect UX does. [Google setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid)
- Load GIS from `https://accounts.google.com/gsi/client`, initialize `google.accounts.id` with the web `client_id`, callback and a fresh nonce, then use `renderButton`. Popup mode returns the ID token in `response.credential`; `prompt()` starts One Tap, which is a separate experience. Send the credential to STREET through the same-origin server boundary. A client ID is public configuration, not a client secret. [JavaScript reference](https://developers.google.com/identity/gsi/web/reference/js-reference)
- GIS requires its generated sign-in button; do not hide it behind a custom button or substitute a custom OAuth button. [Integration guidance](https://developers.google.com/identity/gsi/web/guides/integrate)
- Verify signature against Google's rotating keys, issuer, expiry and an explicitly allowed audience including the web client ID. Use validated `sub` as the provider identity, not email. Google's direct credential POST flow documents double-submit CSRF validation; a custom popup-callback POST still needs its own session-bound anti-CSRF/replay protection. [Server verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
- Check CSP and popup behavior in the deployed browser. Google's setup guide describes required GIS allowlists and potential COOP adjustments when FedCM is unavailable. [Google setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid)

## Sign in with Apple JS

- Apple web sign-in is available to websites and non-Apple devices; do not restrict its display to macOS or Safari. Non-Apple-device users authenticate with their Apple Account and two-factor code. [Apple authentication overview](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple)
- Create/use a **Services ID** for the website and associate it with the existing STREET customer's primary App ID enabled for Sign in with Apple. If the mobile App ID is grouped, identify its primary before configuration. Preserve the existing group rather than creating a disconnected identity configuration. Apple describes grouped credentials as shared through the primary app; verify that an existing mobile user resolves to the same STREET account before release. [Web configuration](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web/), [App grouping](https://developer.apple.com/help/account/capabilities/about-sign-in-with-apple), [Authorization contract](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server.)
- Register the staging domain/subdomain and exact return URL. The return URL must use HTTPS, have a domain name and path, and cannot use an IP address, `localhost`, or a fragment. Use a stable staging HTTPS hostname for provider testing. Apple currently says no domain-verification file upload is necessary. [Authorization contract](https://developer.apple.com/documentation/signinwithapplerestapi/request-an-authorization-to-the-sign-in-with-apple-server.), [Web configuration](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web/)
- Apple's environment guide also states that web authentication requires an existing App Store app using Sign in with Apple. Confirm the existing customer's app satisfies this requirement; registering identifiers alone is not evidence of readiness. [Environment setup](https://developer.apple.com/documentation/signinwithapple/configuring-your-environment-for-sign-in-with-apple)
- Load Apple's hosted JS and initialize with the Services ID, registered `redirectURI`, fresh `state`, fresh `nonce`, requested scopes and `usePopup: true`. Popup success returns `authorization.code`, `authorization.id_token`, and `authorization.state` through a promise/event. The optional `user` object is returned only on initial authorization; returning users must not be required to resupply it. [Webpage configuration](https://developer.apple.com/documentation/signinwithapple/configuring-your-webpage-for-sign-in-with-apple)
- Verify state against the initiating browser transaction and nonce against the signed identity token. Verify the token signature with Apple's public keys, issuer `https://appleid.apple.com`, expiry, and audience equal to the configured Services ID. Accepting the mobile bundle ID alone will reject web tokens. [Nonce](https://developer.apple.com/documentation/signinwithapplejs/clientconfigi/nonce), [User verification](https://developer.apple.com/documentation/signinwithapple/verifying-a-user)
- Apple documents server-side authorization-code validation: exchange the single-use code within five minutes using the Services ID, server-held client secret and the original redirect URI. The client secret is signed using the Sign in with Apple private key associated with the primary app. Private key/client-secret material must never enter browser configuration. A popup delivering an ID token does not itself demonstrate that the existing STREET backend implements this complete web flow. [Token validation](https://developer.apple.com/documentation/SigninwithAppleRESTAPI/Generate-and-validate-tokens), [Environment setup](https://developer.apple.com/documentation/signinwithapple/configuring-your-environment-for-sign-in-with-apple)

## Proposed staging prerequisites

These are implementation recommendations based on the contracts above; configuration names and callback route must be reconciled with the final code before console changes.

| Prerequisite | Value or decision needed |
| --- | --- |
| Marketplace origin | One confirmed, stable staging HTTPS origin; do not infer it from the staging API hostname |
| Google browser configuration | Existing/new public Web OAuth client ID; exact staging origin and local origins registered |
| Google backend audience | Explicitly permit that web client ID while preserving required mobile audiences |
| Apple browser configuration | Public Services ID and one exact registered HTTPS return URL on the chosen staging host |
| Apple identity continuity | Confirm Services ID association with the primary App ID used by existing STREET customers |
| Apple backend support | Explicit Services ID audience, nonce verification, and code-exchange/key configuration if implementing Apple's complete documented web flow |
| Authentication transaction | Server-generated short-lived, single-use challenge tied to browser and provider; reject missing, mismatched, expired or reused state/nonce |
| Account/session boundary | Resolve verified provider identity through existing STREET account rules, then issue the existing HttpOnly STREET session cookies |
| Acceptance evidence | Existing mobile Google/Apple accounts resolve to the same customer on staging; cancellation and popup failure leave the user signed out; invalid audience/state/nonce fails closed |

Keep an unconfigured provider unavailable with a clear explanation. Do not infer provider readiness from a visible button or successful SDK load. Provider console setup, account continuity, and real staging sign-in remain separate acceptance gates.

### Constraints

- **Apple TT-505 remains open.** Current `verifyAppleIdentityToken` validates signature/issuer/expiry but not audience. `loginWithAppleToken` prefers request-body email, computes but does not enforce email verification, and does not use Apple `sub` for persisted identity. The controller does not forward authorization code or user identifier into the service. Do not enable the web button against this flow until shared remediation is approved and verified. [Auth service](../../street-backend/src/modules/v1/auth/services/auth.service.ts), [TT-505](https://linear.app/street/issue/TT-505/street-backend-bind-apple-account-lookup-to-verified-token-claims).
- **Shared backend does not guarantee cross-method deduplication.** `findOrCreateByPhone` matches phone; `findOrCreateByGoogle` (also used by Apple) matches email and creates if absent. An OTP account with no email and a subsequent Google sign-in cannot be matched by those inputs alone. Apple relay email can differ from an existing account's email. Existing same-email switching also replaces the single `ssoProvider` field. [User service](../../street-backend/src/modules/v1/users/services/users.service.ts) (56–110), [repository](../../street-backend/src/modules/v1/users/repositories/users.repository.ts) (20–31, 73–76).
- **Contact email is not proven login ownership.** Profile updates permit changing email after uniqueness checks without verifying ownership; provider login automatically links by that field. An explicit linking flow must prove the existing account and provider identity, rather than promising universal merging based on editable contact details. Tracked in [TT-532](https://linear.app/street/issue/TT-532/street-backend-define-verified-account-linking-across-otp-google-and). [User service](../../street-backend/src/modules/v1/users/services/users.service.ts) (69–110, 145–183).
- **Google is reusable but needs a tight web boundary.** Existing token validation checks Google's tokeninfo and verified email and accepts known client audiences or authorized parties. The marketplace should validate the exact web audience, signed nonce, issuer and expiry before exchanging a credential. Existing shared audience semantics (`aud OR azp`) and stable provider-subject/account linking are part of TT-532. Do not send arbitrary decoded claims as identity. [Auth service](../../street-backend/src/modules/v1/auth/services/auth.service.ts) (422–499).
- The mobile Apple button uses `Platform.isIOS`; that native UI condition is not appropriate for web. Mobile Google uses configured `GOOGLE_SERVER_CLIENT_ID`; Apple requests native credentials with email/name scopes. [Mobile sign-in page](../../street-client-app/lib/app/features/auth/presentation/pages/sign_in_main.dart) (221–266), [Google initialization](../../street-client-app/lib/app/di/injections.dart) (92–97), [Apple service](../../street-client-app/lib/app/core/services/apple_signin_service.dart) (17–22).

Google is now implemented locally on this branch alongside OTP. Google Identity Services renders the official popup button; the Node route verifies Google's signature, exact web audience/authorized party, issuer, expiry, verified email and browser-bound nonce before calling the existing staging endpoint. STREET tokens remain in the existing HttpOnly session cookies. No backend or mobile code changed; Apple stays deferred.

The ten-minute nonce is held in a host-only HttpOnly SameSite cookie and cleared after a same-origin exchange attempt. This prevents ordinary browser reuse after consumption; it is not an atomic, distributed replay ledger against a captured cookie and credential reused together. Concurrent tabs may replace each other's challenge and require retry. A signed-in browser must sign out before choosing a different account.

Automated verification covers cryptographic token rejection, request boundaries, successful session exchange and upstream failures. Browser fixtures exercise Google/OTP success and failure without real account mutations. The real Google widget loads locally without horizontal overflow at desktop and narrow mobile sizes. SDK loading does not prove provider-console authorization or successful sign-in. The user confirmed existing mobile Google account continuity locally: profile, saved addresses and wishlist match, and sign-out/sign-in succeeds. The first attempt returned origin_mismatch; adding the local JavaScript origin to the existing Google Web client resolved it. The deployed Vercel flow still requires acceptance testing.
